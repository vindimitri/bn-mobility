Bonn Mobility — Leitplanken

Kurzüberblick: Verkehrswege des Systems und die Vorgehensweise. Ziel: öffentliche Welo-Plattform für Bonn/Rhein-Sieg mit eigener Historie, später DevOps-Nachweis (Container, Kubernetes, Lastsimulation).

1. Verkehrsdiagramm (gesamter Datenfluss)

Die Website spricht nie direkt mit Welo. Nur Ingestion kennt den externen Feed. Website und Datenbank bleiben außerhalb von Kubernetes.

Blau = Nutzerverkehr · Orange = Schreiben / Verarbeitung · Grün = Lesen aus der DB · Lila gestrichelt = simulierte Last (k6) · Gestrichelter Rahmen = Container-Bereich

Sequenz: was passiert bei einem Kartenaufruf

Parallel dazu (nicht im Nutzerklick): Ingestion pollt Welo regelmäßig und schreibt Snapshots. Analytics liest Snapshots und schreibt Kennzahlen. k6 simuliert später viele parallele Schritte 1–4.

2. Vorgehensweise (deduktiv, kurz)

Von innen nach außen: erst Datenpfad, dann Website, dann Container, dann Cloud-Kubernetes und Last.

  1. Fundament: Schema in Supabase (stations, station_snapshots, ingest_runs). GBFS-Client: ein erfolgreicher Poll speichert echte Welo-Daten.
  2. Live-Pfad: Read-API /v1/stations, Karte auf Vercel, Domain (IONOS DNS → Vercel). Browser spricht nur uns.
  3. Historie: regelmäßige Snapshots, Retention, Station-Kurve, einfacher Health-Wert. Optional Flexzonen-Räder als zweiter Layer.
  4. Container lokal: Ingestion, API, Analytics als Docker-Images, Compose auf dem PC. Ein Container neu starten, Rest läuft weiter.
  5. Cloud-Kubernetes: dieselben Images deployen. Healthchecks, Limits, Rolling Updates. Ingestion = 1 Replica; API darf skalieren.
  6. DevOps-Nachweis: Prometheus/Grafana, k6 mit simulierten Nutzern gegen Karte/API, Autoscaling und Ausfalltest dokumentieren.
Gate-Regel: Keine Phase überspringen. Ohne stabile Snapshots kein sinnvolles Kubernetes. Ohne drei laufende Container keine Last-Demo.
